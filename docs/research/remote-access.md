这次讨论起于 #70 的 Web 工作台。最初是在看这个 PR 是否适合合入，聊着聊着发现，它背后有一个值得展开的需求：**项目和开发环境留在一台机器上，人能不能换个地方、换个设备，继续操作它？**

顺着这个需求，我们想到了三条可以相互配合的线路：客户端之间远程操作、客户端开放 Web 入口，以及未来的无头 Linux 客户端。

## 先把使用场景说清楚

用三台机器来理解会比较直观：A 运行 Claude Code，B 放项目、编译器和开发工具，C 是人此刻手边的设备。

现在，B 同时承担开发执行和操作界面两个角色。人坐在 B 前面时很自然，但如果任务跑在办公室电脑上，人已经回家，或者只是离开座位想用手机看看进度，就需要远程桌面回到 B。

#70 做的是让 B 再提供一个 Web 入口。人在 C 上打开浏览器，就能通过 B 的客户端继续发消息、看进度、处理审批。Claude Code 仍在 A 上运行，命令仍回到 B 执行。这个需求是成立的，尤其适合手机和平板上的轻操作。

讨论到这里，一个更一般的想法出现了：**既然项目不用跟着人走，那么操作界面也不必一直和项目放在同一台机器上。**

## 线路 1：把“其他设备”用起来

我们已经支持多个客户端同时连接一个服务端，也能在“其他设备”里看到别的电脑上的会话。由此很自然地想到：既然已经看得见，能不能直接在这里继续操作？

比如 B 上的任务还在跑，C 打开这个会话，就可以继续提问、回答审批或停止任务，执行仍留在 B。之后还可以在 B 的项目下创建新会话。这样回家用笔记本操作办公室电脑，就不必先把项目复制过来，也不必把会话接管到笔记本上。

现有的“在本机继续”和“分叉到本机”仍然有用：它们适合确实想换开发机器的时候。这里增加的是另一种选择——**我只换操作位置，继续用原来的开发环境。**

“其他设备”的界面也可以顺势补上在线状态。至少应该让人知道：这台设备现在可用、正在连接，还是已经离线。点击进去以后，能否发送消息、为什么暂时不能操作，都有清楚的依据。

从现有实现看，这条路有不错的基础。运行已经会按设备寻找执行通道，主要需要把“谁发来的指令”和“在哪台设备执行”分开。目前发消息、审批等操作要求来自会话所在设备，新建会话也默认归发送者；这些地方需要统一调整，同时补上设备状态和目标项目的处理。

难点主要在几个人手入口同时操作同一会话时如何保持一致：两端都看见审批，哪一端先回答就同步结果；C 关掉客户端，B 上的任务继续；B 真正离线了，C 能看懂当前在等什么。这些值得集中做一轮回归。

这条线路与现有架构贴合，也能直接覆盖多电脑使用的场景，我们倾向优先做。只要 B、C 都能连到 A，就不需要 C 直接访问 B。也欢迎 #70 作者一起参与，“其他设备”的状态和控制入口都很适合作为合作的起点。

## 线路 2：给客户端接出一个 Web 入口

线路 1 适合已经安装客户端的电脑，Web 则补上手机、平板和临时浏览器。两者互补，可以各自推进。

我们对 Web 端的期待是：它像把客户端的操作界面接出去，浏览器里的一项操作，最终调用的还是客户端已有的那项能力。页面、业务逻辑和执行通道尽量共用，Web 增加的是访问方式。

这里最重要的要求是：**无论开不开 Web，原客户端内部的行为都应保持原样。** 开关 Web、刷新网页、关闭浏览器，不应打断桌面连接或已有任务；桌面原来的退出、重连和定时任务也应照常工作。

因此，“轻量”主要体现在改动边界上。认证、网络传输和浏览器适配需要一些新代码，这很正常；但如果为了接入 Web，桌面本身也必须换一套连接和状态管理，就需要先把这部分理顺。

前面阅读 #70 时，这里确实有一个需要继续讨论的地方：当前实现即使关闭 Web，桌面连接也会经过新增的控制汇聚层，同配置重连的处理也发生了变化。希望作者优先把这一点收敛好，让 Web 真正成为现有客户端的外接能力。

功能上，我们希望作者把主要流程做完整，再考虑合入。除了聊天和审批，还需要把几个容易产生差异的地方交代清楚：浏览器选择的是 B 上的项目，上传的附件如何交给 B，多个页面怎样同步，定时任务如何保证只触发一次。窗口控制、安装器这类桌面专有能力，可以留在桌面端。

设置里提供开关、端口和授权管理即可。现有随机配对码可以继续完善，浏览器登录补上有效期和撤销机制，关键测试也一并提交，方便后面维护。

至于从外网怎样连到 B，交给使用者自己的网络条件、组网或反向代理。这个 Web 入口先把“能够访问并通过鉴权，就能操作客户端”做好，不必把公网中继一起背上。

整体上认可这个方向，也希望 #70 作者继续做。我们更愿意等一个边界清楚、主要流程完备的版本；如果还需要时间，就先攒一攒。

## 线路 3：B 可以是一台无头 Linux 机器

前两条线路把操作界面从 B 上移开后，又引出了一个想法：**既然人可以从别处操作 B，B 为什么还一定要有桌面界面？**

它完全可以是一台常开的 Linux 工作站、家用服务器或云机器，上面放着项目、依赖和工具链。一个无头客户端负责连接 A、维持执行通道，人在 C 上通过“其他设备”操作它。需要浏览器时，再给它启用 Web 入口。

这样三个角色就更加清楚了：A 跑 Claude Code，B 承担实际开发任务，C 提供人使用的界面。日常使用优先走线路 1，Web 作为补充。

这也解释了为什么讨论时会联想到“云电脑 bot”一类产品。吸引人的地方是：有一台机器持续保留工作环境、承接长任务，人只需要在方便的时候看进度、处理审批、补充指令。远程开发环境强调的是环境留在远端，手机控制 agent 强调的是操作入口随人走；这两种思路在这里接上了。

像 Coder 的远程开发环境、Happy 的手机控制会话，都可以作为这种体验的参考。对我们来说，最值得延续的特点是 A 和 B 仍然可以分开：Claude Code 跑在哪里，与项目需要什么开发环境，可以分别安排。

这还和之前两个讨论有关。#9 已经涉及 Linux 客户端和后台运行，可以继续复用其中的执行能力；#44 希望界面在 Windows、真正的开发在 Linux。如果 Linux 能直接连接 A，无头客户端就提供了一条很自然的实现路径，Windows 也不用一直开着充当跳板。

已有 Linux 执行模块和连接通道是基础，接下来主要需要补命令行配置、凭据保存、后台运行、日志和独立打包。定时任务目前还依赖桌面界面中的逻辑，无头运行时也要一起梳理。因此这条先记作后续方向，优先在线路 1 打通以后推进。

## 接下来怎样推进

先完善“其他设备”的状态和远程操作能力，解决另一台客户端继续驱动 B 的需求。#70 可以并行完善 Web 入口，重点守住原客户端行为不变、业务能力共用这两点。等操作端与执行端的关系清楚了，再把无头 Linux 客户端接上来。

这三条线路来自同一个想法：**开发环境留在合适的机器上，人从方便的地方继续工作。**
